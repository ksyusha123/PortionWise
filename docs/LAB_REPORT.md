# Практическая работа № 13: дневник питания

Это заготовка отчёта. Скриншоты и наблюдения необходимо добавить после запуска; текст ниже не утверждает, что реальные Telegram/Yandex-вызовы уже выполнены.

## Цель

Разработать микросервисное приложение с сетевым взаимодействием, независимыми хранилищами и контейнеризацией.

## Архитектура

Три бизнес-сервиса на Go: User Service (профили и вход), Analysis Service (VLM и квоты), Diary Service (записи и суммы). Telegram Bot — отдельный интерфейсный процесс. Диаграмма приведена в README. Каждый компонент имеет собственную SQLite-базу и Docker volume. Базы других сервисов недоступны; общение через HTTP. Обнаружение — DNS-имена Docker Compose.

## Демонстрация

1. Скриншот `docker compose ps`: три сервиса healthy, бот запущен.
2. Скриншот `/start`, настройки часового пояса и нормы.
3. Фото → предварительный анализ → изменение массы → сохранение.
4. Ручное добавление → дневной итог → изменение и удаление записи.
5. Достижение дневного лимита; ручной ввод остаётся доступен.
6. Остановка Analysis Service; дневник работает, новое фото даёт понятную ошибку.
7. Возобновление сервиса и повторная проверка.
8. Результат `go test ./...`.

Если использовался `AI_MODE=mock`, явно указать это. Для утверждения о реальной VLM-интеграции необходим отдельный запуск с `AI_MODE=yandex` и рабочим ключом.

## Принципы

- Сетецентричность: межсервисные вызовы только HTTP.
- Автономность: отдельные процессы, Dockerfile и хранилища.
- Слабая связанность: контракт API, дневник хранит свой снимок анализа.
- Stateless backend: состояние запросов хранится в БД, не в глобальных пользовательских переменных.
- Обработка сбоев: сетевые таймауты, понятные ошибки, возврат квоты при технической ошибке, идемпотентность.
